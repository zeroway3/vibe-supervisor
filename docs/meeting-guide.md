# 보안담당자·심사원 미팅 가이드

멘토링으로 연결되는 ISMS-P 보안담당자(또는 심사원) 미팅용. 목표는 기능 설명이 아니라
**"이 결과물을 실제 증빙으로 쓰겠다 / 써보겠다"는 근거를 남기는 것**이다. 2라운드
심사에서 내밀 수 있는 건 미팅 기록과 파일럿 의향뿐이다.

---

## 1. 미팅 전 준비물

- [ ] 노트북에서 `npm run build && bash demo/run-demo.sh` 리허설 (인터넷 안 되면 `DEMO_OFFLINE=1`)
- [ ] Docker Desktop 실행 + `semgrep/semgrep:1.95.0` 이미지 미리 받아두기 (현장 다운로드 금지)
- [ ] 발표용은 `DEMO_PAUSE=1`로 단계마다 멈춰 가며 설명
- [ ] 시연으로 만든 `report.html`을 브라우저에서 열어 PDF로 저장 → 출력본 2부 (상대방이 펜으로 표시할 수 있게).
      인쇄 설정에서 '머리글/바닥글'은 끄고 '배경 그래픽'은 켠다
- [ ] 이 문서의 질문지 출력본, 녹음 동의 문구

## 2. 시연 순서 (10분)

| 시간 | 장면 | 한 줄 메시지 |
|---|---|---|
| 1분 | 설치 → AI 트레일러 커밋 → 커밋 시점에 3건 탐지 | "개발자는 평소대로 커밋만 합니다" |
| 2분 | 수정 커밋 → 재검사에서 사라짐 안내 → 조치 완료 1건 / 예외 1건(사유 필수) | "처리한 그 순간이 기록됩니다. 고쳤다는 것도 재검사 기록이 뒷받침합니다" |
| 1분 | 외부 타임스탬프 등록 | "이 시각에 이 기록이 있었다는 걸 제3 기관이 서명합니다" |
| 2분 | 리포트 출력본 넘기기 | "1장이 ISMS-P 2.8 대응 범위 — 못 하는 것도 적었습니다" |
| 4분 | 변조 3종 시연 (사유 몰래 수정 / 원장 없이 승인 / 원장 통째로 재생성) | "고치면 걸립니다. 다시 만들어도 걸립니다" |

시연 직후 바로 질문으로 넘어간다. 기능 설명을 더 하지 않는다.

## 3. 질문지 — 보안담당자용 (구매자)

순서대로. 앞 질문 답이 "아니요"면 뒤 질문을 억지로 하지 않는다.

**현재 상태 (문제가 실재하는가)**
1. 개발보안(2.8) 증빙은 지금 어떤 자료로 내고 계세요? (예: 진단 도구 리포트, MR 승인 화면 캡처, 점검표)
2. 그 자료를 만드는 데 연간 몇 명이 며칠 정도 쓰나요? 외부 컨설팅 비용 중 이 부분 비중은?
3. 심사에서 개발보안 쪽으로 지적받았거나 추가 자료를 요구받은 적이 있나요? 어떤 내용이었나요?
4. 개발팀이 AI 코딩 도구를 쓰고 있나요? 그와 관련해 정해진 정책이나 고민이 있나요?

**결과물 평가 (쓸 수 있는가)**
5. 방금 리포트를 심사 때 제출하신다면, 그대로 낼 수 있는 부분과 안 되는 부분은 어디인가요?
6. **지금 쓰시는 GitLab/GitHub 승인 기록이나 진단 리포트와 비교하면 무엇이 더 낫고 무엇이 부족한가요?**
   (가장 중요한 질문. "충분하다"는 답이 나오면 왜 충분한지 끝까지 들을 것)
7. 1장의 조항 매핑(2.8.1~2.8.6)에서 틀렸거나 과장된 곳이 있나요?
8. AI 출처(확정·추정·미상) 정보가 심사에 의미가 있나요, 아니면 내부 관리용인가요?
9. 승인자가 git 이메일 기준인데, 심사에서 이 정도면 되나요? 아니면 서명·SSO가 꼭 필요한가요?

**도입 가능성 (살 것인가)**
10. 이런 도구를 도입한다면 어느 예산에서, 누구 결재로 나가나요?
11. 소스코드가 외부로 안 나가는 로컬 방식인데, 그래도 보안성 검토나 도입 심의가 필요한가요? 기간은?
12. **사내 저장소 하나에 2~4주 파일럿을 해보실 수 있을까요?** 안 된다면 무엇이 걸리나요?

## 4. 질문지 — 심사원용 (수용 여부 판단)

1. 개발보안 영역에서 심사원이 실제로 확인하는 증빙은 무엇인가요? 가장 흔한 결함 판정 사유는?
2. 이 리포트가 제출되면 증빙으로 인정하시겠어요? 인정한다면 어느 조항, 안 된다면 무엇이 빠졌나요?
3. 해시 체인과 외부 타임스탬프 수준의 무결성 보장이 심사에서 의미가 있나요, 과한가요?
   (지원서 Q4-2 멘토 질문 1번 — "과한 설계는 비용, 부족한 설계는 제품 불성립"의 선)
4. 인증 후 상시점검이 강화되면 이런 상시 기록의 가치가 달라지나요?
5. 조항 매핑에서 틀린 곳을 짚어주실 수 있나요?

통과 기준(지원서 Q4-1): 심사원 3인 중 2인 이상이 "심사 자료로 쓸 수 있다".

## 5. 미팅에서 반드시 남길 것

| 남길 것 | 형태 | 2라운드에서의 쓰임 |
|---|---|---|
| 인터뷰 기록 | 동의 받은 녹음 또는 당일 정리한 메모 (상대 직함·조직 규모 포함, 실명은 동의 시에만) | 문제 실재 근거 |
| 지적받은 부족한 점 목록 | 메모 → 바로 이슈로 등록 | "피드백 받아 고쳤다"는 반복 근거 |
| 파일럿 의향 | 이메일 한 줄도 충분 (아래 문구) | **가장 강한 근거** |
| 소개 | 다른 담당자·심사원·컨설팅사 연결 | 표본 늘리기 |

파일럿 의향 확인 메일 예시:

> 오늘 시간 내주셔서 감사합니다. 말씀 주신 [부족한 점]을 보완한 뒤, [회사명]의 저장소 1곳에
> 2~4주간 바이브 슈퍼바이저를 시범 적용해 보는 것에 대해 긍정적으로 검토해 주신다고
> 이해했습니다. 맞는지 회신 부탁드립니다.

## 6. 예상 반론과 답

| 반론 | 답의 방향 |
|---|---|
| "MR 승인 기록이면 충분하다" | ① 보안 지적사항과 조치·예외 승인을 한 이력으로 묶음 ② Git 서버 관리자도 고칠 수 없는 외부 앵커 ③ 같은 룰셋으로 6개월 뒤 재현. 그래도 충분하다면 **그 답을 그대로 기록** — 피벗 근거가 된다 |
| "AI 출처는 심사 항목이 아니다" | 동의. 핵심은 검토·승인 이력의 무결성이고 출처는 부가 정보. AI 비중이 커질수록 묻게 될 질문을 미리 답해 두는 것 |
| "트레일러는 개발자가 안 쓰면 그만 아닌가" | 맞다. 그래서 '미상'을 숨기지 않고 비율로 표기한다. AI 도구가 자동으로 붙이는 공동작성자 표기는 '추정'으로 잡는다 |
| "승인자 이메일은 위조 가능" | 맞다. 리포트 한계 항목에 적어 두었고, 다음 단계는 서명 커밋/SSO. 어느 수준이 필요한지 여쭙고 싶다 |
| "탐지 룰이 4개뿐" | 탐지는 경쟁 영역이 아니다. Semgrep·상용 도구 결과를 SARIF로 받아 같은 원장에 묶는 게 설계 방향 |
